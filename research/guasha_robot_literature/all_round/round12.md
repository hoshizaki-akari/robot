# 第12轮：先证明机器人和力传感器真的可用，再挑选力控算法
> 学习目标：看完后能解释为什么“有一个 API”不等于“有实时闭环”，为什么六维力/力矩数据必须逐轴验真，以及为什么论文里表现最好的控制器不一定是 FR5 上可实现的 baseline。

## 1. 本轮问题（为什么重要）

前几轮已整理接触坐标系、CoP、曲面跟随和多种导纳控制方案。但它们都有共同前提：机器人命令真的按预期执行，传感器输出可信，并且命令、力与位姿使用统一坐标和时间基准。

本轮先回答三个问题：
1. FR5 实际控制入口是供应商 SDK、ROS 2 service，还是已经具备兼容 ros2_control 的硬件接口？
2. KWR75D 六维数据能否证明每个轴都正确，没有卡零、通道重复、单位缩放或明显时间错位？
3. 在这些前提通过之前，哪种控制方法能成为真正可复现的 baseline？

结论：**先做 G0 接口与传感器健康检查，暂时不冻结最终控制算法，也不宣称核心创新已经成立。**

## 2. 前置知识

### SDK 是什么？
SDK 是程序调用机器人功能的一组接口。它可能提供读位姿、移动到某点、开启传感器等方法。但 SDK 中有某个方法不代表它一定高频、无阻塞、实时，也不代表现场固件支持且传感器有有效输出。

### ROS 2 service 与 ros2_control 有什么不同？
service 通常是一问一答；ros2_control 有明确的硬件命令接口、状态接口和控制器更新架构。将 SDK 方法包装成 service 有助于集成，但 service 不会自动变成实时硬件接口。

### 六维 wrench 是什么？
它包括三轴力和三轴力矩：
\[
\mathbf w=[F_x,F_y,F_z,\tau_x,\tau_y,\tau_z]^\top.
\]
力和力矩必须绑定正确的表达坐标系和参考点。参考点一换，力矩就会变化。六个数字不意味着通道、符号、单位和时间戳都正确。

## 3. 核心讲解

### 3.1 供应商 SDK 与 ROS 2 API 不能按名字推断性能
FAIRINO 的 Python SDK 与 frcobot_ros2 是两条公开软件入口。ROS 2 仓库 README 描述将部分功能包装成 service，并规定了机器人软件版本要求。SDK 发布标签也存在与控制器软件版本配对的命名。

设备登记表必须记录控制器固件、SDK 版本、ROS 2 驱动分支、机器人型号和传感器版本。不能因为本地 Python 能导入模块就认为它与现场控制器兼容，也不能因为 ROS 2 能调用运动 service 就认为它具备实时导纳所需的硬件接口。

### 3.2 标准导纳控制器需要的不只是一个 F/T topic
上游 ros2_control admittance controller 需要支持的关节命令/状态接口、运动学插件、base/tip 定义、F/T sensor frame、控制框架与固定世界框架，以及末端质量/重心等重力补偿配置。

如果只有外部 ROS topic，没有与 controller manager 正确连接的硬件状态/命令接口，就不能直接假设该控制器可运行于 FR5。即便编译通过，坐标、补偿和反馈时间仍需要验证。

### 3.3 用用户 issue 生成测试用例，不把它当成缺陷结论
公开 issue 有用户报告 F/T API 读数全零，也有标题报告特定固件版本下通道疑似重复。这不等于厂商已确认系统缺陷。更稳妥的方法是把每种风险转换为测试：全零检测、六轴独立激励、符号/单位核对、硬件与固件版本记录、重复帧检测。

API 返回成功码只说明请求层未返回错误，不保证传感器在输出有效数据。UI 与 SDK 若共享同一内部数据源，也不能算独立真值。

### 3.4 控制 baseline 必须根据执行接口选择
自适应导纳论文提供在线法向与参数调整方案；显式力/力矩控制论文提供动态力跟踪的强参照。但这些不能直接推出 FR5 的能力。如果实际路径只是带一定延迟的笛卡尔位置外环，第一版应使用固定参数、有界更新的导纳作为简单基线，并测自适应版本是否有真实收益。只有当接口支持其命令与状态语义时，显式力控才能成为实现层面的公平对照；否则只能作为论文参照。

## 4. 公式直觉

### 4.1 延迟不会因“提高循环频率”而消失
假设程序周期为 T_s，从发命令到收到对应真实反馈还有延迟 τ。此时控制器用到的力读数可能对应更早的接触状态。只提高程序频率，却不管数据新鲜度、服务阻塞和运动命令队列，可能只是更快重复发送过期信息。

至少应测量命令到运动延迟、力数据到命令的路径延迟、反馈周期及其抖动。所有这些都需从共同时间基准的日志中估计，不能将文档中的最高调用频率当作闭环带宽。

### 4.2 wrench 从末端参考点移到接触点
设 E 是末端参考点，C 是接触点，r_EC 是从 E 指向 C 的向量，且力、力矩表达在同一坐标系，则：
\[
\boldsymbol\tau_C=\boldsymbol\tau_E-\mathbf r_{EC}\times\mathbf F.
\]
符号取决于向量方向和 wrench 约定。代码要用已知力臂、已知方向的载荷试验校验，不可只复制公式。

若接触点也随时间变化，其速度同样需要更新：
\[
\mathbf v_C=\mathbf v_E+\boldsymbol\omega_E\times\mathbf r_{EC}.
\]
所以动态 contact frame 不是只改一个位置变量；wrench 参考点、接触点速度、姿态误差和 Jacobian 必须遵循同一个坐标定义。

## 5. 未解问题与失败边界

1. 现场 FR5 固件和实际安装 SDK/驱动版本尚未登记，当前不能给出匹配版本结论。
2. 公开接口资料没有证明本机命令—反馈延迟、抖动、队列行为或接触力闭环带宽。
3. KWR75 系列公开驱动不能仅凭型号前缀推定当前 KWR75D 变体、适配器与固件匹配。
4. 用户 issue 只提示风险，不能据此确定根因或修复状态。
5. 宽刮板单腕 F/T 合 wrench 不等于完整接触压力图；不可辨识时应增加独立传感信息或收窄估计声明。
6. 跨任务控制方法必须在相同轨迹、相同过滤、相同时间戳和相同安全边界下重新对比。

## 6. 记住的三件事

1. **软件接口存在，不等于实时闭环能力已经被证明。**
2. **六维力/力矩必须通过独立参考、已知力臂和逐轴激励来验真。**
3. **先测真实机器人和传感器的时序，再选控制 baseline，最后才讨论算法创新。**
