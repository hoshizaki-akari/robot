# 专题研究线 A：FR5 / KWR75D 官方接口、实机可执行性与时间同步审计

> 日期：2026-10-10  
> 类型：专题审计，**不是完整 Run**；不占用 daily Run 编号，不修改共享索引。  
> 研究目的：用可核验证据判断哪条机器人命令/反馈路径值得进入 G0 台架验证，并提前发现 KWR75D 驱动、量程和时间戳的集成风险。  
> 本报告没有连接实际 FR5/KWR75D，也没有下载、编译或运行驱动；代码结论来自公开源码静态检查，所有实机性能仍标记为待测。

## 1. 本轮只回答的三个决策问题

1. **FR5 的哪条接口路径可作为控制实验候选？** 区分厂商 SDK、ROS 2 service wrapper 与 `ros2_control` 硬件接口；特别区分“指令函数存在”“调用返回成功”“机器人完成运动”和“可用的高带宽闭环”。
2. **公开 KWR75 ROS 2 驱动能否直接用于 KWR75D？** 核对厂商 KWR75D 规格与驱动硬编码范围、单位转换、协议解析和时间戳实现。
3. **在选择导纳/显式力控前，必须先做什么最小安全实验？** 定义同步日志、频率/延迟/丢帧指标与停止验证门槛；不开展真人接触。

## 2. 关键结论（按工程决策优先级）

### 结论 A1：当前不能仅凭 SDK 或 ROS 2 API 名称认定 FR5 具备合适的实时力控接口

FAIRINO 维护的 `frcobot_ros2` README 将该项目描述为基于 Fair SDK 的 ROS 2 API，并说明通过 service message 暴露函数；README 还指出软件版本需高于 V3.7.1。官方仓库按机器人软件版本保留多个硬件包，最近可见提交之一为 2026-09-23 的 `fcf0c7f0d60d949d8a9a4238f929a44d07f60379`，其中新增适配 V4.0.0 的包。这说明版本配对是实质约束，不应只装“最新分支”后假定兼容。

- 官方仓库：[FAIRINO/frcobot_ros2](https://github.com/FAIR-INNOVATION/frcobot_ros2)
- 版本适配提交：[fcf0c7f](https://github.com/FAIR-INNOVATION/frcobot_ros2/commit/fcf0c7f0d60d949d8a9a4238f929a44d07f60379)
- 官方仓库 README：[README.md](https://github.com/FAIR-INNOVATION/frcobot_ros2/blob/main/README.md)

公开的 SDK 头文件中存在 `ServoCart(..., cmdT, filterT, gain)`、`ServoMoveStart/End` 等接口；版本化命令服务器还暴露 `StopMotion`、`PauseMotion`、`ResumeMotion`，状态头文件包含急停状态查询。**静态存在这些函数，只能证明 API 表面存在，不证明具体固件下的参数语义、实际执行周期、停止距离或安全等级。** `StopMotion` 也不能未经验证就当作安全级急停替代品。

- 可核验的版本化 SDK 头文件：[FR5 V3.9.7 包中的 robot.h](https://github.com/FAIR-INNOVATION/frcobot_ros2/blob/fcf0c7f0d60d949d8a9a4238f929a44d07f60379/fairino_hardware_v3_9_7/libfairino/include/robot.h)
- 同版本命令接口声明：[command_server.hpp](https://github.com/FAIR-INNOVATION/frcobot_ros2/blob/fcf0c7f0d60d949d8a9a4238f929a44d07f60379/fairino_hardware_v3_9_7/include/fairino_hardware/command_server.hpp)

**额外风险信号（非厂商确认的缺陷结论）：** 官方仓库的公开 issue #35 记录了 FR5 V6.0、机器人软件 v3.9.7、ROS 2 Humble 与对应版本硬件插件在 activation 阶段崩溃的用户报告；issue #36 记录了 ROS 2 Jazzy / FR5 V6.0 环境下 MoveL service 返回成功但运动仍未结束、以及分段运动异常停止的用户报告。这些 issue 不能证明所有设备都会出现问题，但足以说明必须按现场固件/SDK/驱动版本实测，且不能把 service 成功码当作“轨迹执行完成”。

- [Issue #35：硬件插件激活崩溃报告](https://github.com/FAIR-INNOVATION/frcobot_ros2/issues/35)
- [Issue #36：MoveL 返回与运动完成语义报告](https://github.com/FAIR-INNOVATION/frcobot_ros2/issues/36)

**本项目决策：** G0 未通过前，不把显式力/力矩控制列为已可实现的主控制器。先用与现场版本严格匹配的厂商 SDK 进行低风险命令/状态审计；ROS 2 service 适合作为监督层候选，但除非实测证明延迟、抖动和执行完成语义满足要求，不把普通 service 调用放入快速力控环。只有当具体 `ros2_control` 硬件接口的固件兼容性、命令/状态接口和更新时间均验证后，才将其与上游导纳控制器集成。

### 结论 A2：KWR75D 与公开 KWR75 ROS 2 驱动存在需要先修正/验证的规格不匹配

坤维官方 KWR75 系列页面给出的 KWR75D 规格为：

| 项目 | 厂商页面给出的 KWR75D 值 | 对本项目的含义 |
|---|---:|---|
| Fx/Fy 量程 | 500 N | 应按确切型号设置量程与异常判定 |
| Fz 量程 | 700 N | 不能沿用其他型号的量程常数 |
| Mx/My/Mz 量程 | 18 N·m | 同上 |
| 采样频率 | 1000 Hz | 这是规格值，不是本机串口/ROS 数据流实测值 |
| 分辨率 | 0.03% FS | 需按各轴满量程换算，并以实际采集模块为准 |
| 准度 | 0.5% FS | 若目标刮拭力较小，满量程误差可能成为重要预算项；需厂商确认该指标对所购传感器/数采模块的具体定义 |

来源：[坤维 KWR75 系列官方产品页](https://www.kunweitech.com/products/866.html)。该页面还提示部分参数与配套数采模块有关。因此，不能仅凭“KWR75D”型号推断实际输出协议、采样时钟、滤波、单位或延迟；必须核对订单/铭牌上的传感器和数采模块组合。

对照公开 ROS 2 驱动 `ian-chuang/kwr75_force_sensor_ros2`（分支 `humble`）的静态代码审查：

- README 声称测试环境为 Ubuntu 22.04 + ROS 2 Humble；不是对所有 ROS 2 发行版的兼容保证。
- 代码发送 `0x48 AA 0D 0A` 启动命令，并按其所引用协议解析 28 字节帧。
- 代码将前三个浮点通道乘以 9.81 转成 N，将后三个通道乘以 9.81 转成 N·m；这是该驱动对当前协议/数据格式的假设，必须用实际原始帧和已知载荷确认。
- 头文件硬编码 `MAX_FORCE = 200 N`、`MAX_TORQUE = 8 N·m`。这与厂商表格中的 KWR75D 满量程（500/700 N、18 N·m）不一致。它可能在较低载荷下仍能输出，但超过硬编码阈值时会报 out-of-range；因此**不能不经配置审查就把该驱动作为 KWR75D 的 drop-in 驱动**。
- 接收回调只记录主机 `steady_clock` 的最近接收时间，用于数据看门狗；ROS 2 state interface 未暴露每个传感器样本的设备采样时间。读取函数读取最新缓存值，因此主循环看到的更新时间不等于传感器采样时间。
- 帧解析器每次回调只选取缓冲区中最后一个完整帧并更新数据，没有循环逐帧消费所有完整帧。如果一次串口回调包含多个完整帧，较早帧可能被跳过。此为**静态代码推断，未通过实机复现**，必须用原始字节流/帧计数测试确认。
- 仓库许可证为 Apache-2.0；最近可见提交 `a68e4d5da63ca1c6b2c0733cab24df21535c0db9`（2024-04-05）明确修改 force/moment 单位注释与转换。

资源：
- [KWR75 ROS 2 驱动 README](https://github.com/ian-chuang/kwr75_force_sensor_ros2/blob/humble/README.md)
- [驱动源码 hardware_interface.cpp](https://github.com/ian-chuang/kwr75_force_sensor_ros2/blob/humble/src/hardware_interface.cpp)
- [驱动头文件及硬编码量程](https://github.com/ian-chuang/kwr75_force_sensor_ros2/blob/humble/include/kwr75_force_sensor_ros2/hardware_interface.hpp)
- [Apache-2.0 LICENSE](https://github.com/ian-chuang/kwr75_force_sensor_ros2/blob/humble/LICENSE)
- [单位转换相关提交](https://github.com/ian-chuang/kwr75_force_sensor_ros2/commit/a68e4d5da63ca1c6b2c0733cab24df21535c0db9)

**本项目决策：** 保留该驱动作为协议/ROS 2 硬件接口参考，不直接作为最终控制输入。先确定实际串口/数采协议与 baud rate；用已知六轴载荷验证符号、比例、串扰、零点、量程；检查每个输入帧是否恰好被处理一次，并在消息接口显式携带主机接收时间、样本序号、有效性和数据年龄。若设备协议没有硬件采样时间戳，必须把 `host_receive_time` 与 `sensor_sample_time=unknown` 区分，不能伪造采样时间。

### 结论 A3：控制器选型的第一道门是测清命令—运动与传感器数据链，而非直接调导纳参数

推荐分层路径：

1. **G0-a：厂商 SDK / 状态读取** — 锁定 FR5 型号、控制器固件、WebApp/控制器版本、SDK tag/commit、ROS 发行版和驱动 tag。读回实际 TCP/关节状态、运动状态、错误码/安全状态。
2. **G0-b：KWR75D 数据链** — 保存原始字节流与解码后的六轴值；测真实帧率、重复/丢失帧、接收间隔、时间抖动、零点漂移与六轴已知载荷误差。
3. **G0-c：命令完成与停止** — 在空旷、无接触、受限工作空间中，以经风险评估批准的低速、小位移命令验证命令被接受、实际运动开始/结束、暂停/普通停止响应、状态反馈和物理急停流程。必须由独立人员/机制监控停止，不以待测软件作为唯一保护。
4. **G0-d：运动频响** — 仅在 G0-a–c 通过后，对安全无接触小幅轨迹执行阶跃/多频正弦或 chirp，记录命令与实际 TCP/关节反馈，计算延迟、抖动、幅值衰减、相位滞后与跟踪误差。
5. **G0-e：体模接触力响应** — 只有运动环与 F/T 数据链验证通过后，才在有独立参考测力计的软体体模上进行小幅、风险评估批准的力扰动；比较固定参数导纳与候选控制，不进行真人接触。

不要先规定一个未经实测的“FR5 外环带宽”。测试频率范围应由厂商允许的命令周期、实测反馈率、工作空间和风险审查共同决定，并从低频逐级提高；任何异常、状态数据超时、通信丢失或停止路径失效都应终止当前试验。

## 3. 最小实验规范：必须记录什么

### 3.1 统一日志字段

所有节点记录主机单调时钟 `t_host_monotonic`，另存 ROS 时间 `t_ros`（用于可视化/跨系统关联，但不可替代单调时钟）。如果控制器/相机/传感器提供设备时间戳，原样保存并记录时钟域；未验证同步前不直接相减不同设备时钟。

最少记录：

- FR5：命令发送时间、命令序号、命令类型/参数、返回码、实际 TCP/关节反馈接收时间、设备时间戳（若存在）、目标与实际位姿、速度、运动完成标志、主/子错误码、急停/安全状态。
- KWR75D：原始串口字节/帧、帧序号、主机接收时间、解码时间、六轴原始值与换算值、量程/有效标志、丢帧/解析失败/重复值计数、最后新样本年龄。
- 试验：机器人固件、SDK/驱动 commit、ROS 发行版、传感器/数采型号、baud rate/协议、TCP 与 F/T 安装参数、负载/CoG、采样配置、停止事件与人工标记。

### 3.2 指标与验收逻辑

- 反馈与传感器：均值/中位数/P95/P99/最大采样间隔、周期抖动、帧丢失率、重复/陈旧样本率、长尾超时、启动/停止数据延迟。
- 运动环：命令至首个可测运动的延迟、命令—反馈延迟分布、跟踪误差、幅值比、相位滞后、超调、异常停止与恢复情况。
- 力数据链：六轴比例/符号误差、零点与温漂、重复性、已知力臂下的力矩误差、交叉轴耦合；用独立校准测力设备或已知载荷/力臂作为参考。
- 安全：普通 StopMotion、PauseMotion 与物理急停分别测试；记录触发至停止运动的时间、停止距离/姿态、状态反馈是否一致。软件停止与安全级急停分开验收。

验收阈值不在本报告中臆造：应由机器人/传感器手册、预先批准的风险评估、目标力/速度和误差预算确定。先定义阈值，再做实验，不能根据结果事后放宽标准。

## 4. Baseline 与路线选择矩阵

| 路径 | 适合用途 | 当前证据 | 主要风险 | 决策 |
|---|---|---|---|---|
| 厂商原生 SDK（C++/Python） | G0 状态/命令语义审计；低风险运动基线 | 官方仓库与 SDK 声明存在 | 具体版本、调用周期和反馈时序未实测 | **第一步采用**，先只做读状态与受限空载运动 |
| 厂商 ROS 2 service API | 上层监督、调试和普通运动命令 | 官方 README 明确为 service wrapper | service 返回值可能只代表接受/函数执行结果；不等于运动完成或实时控制 | 不直接放入快速力控环，除非实测证实 |
| 版本匹配的厂商 `ros2_control` 硬件插件 | 可能作为 ROS 2 控制器的状态/命令接口 | 官方仓库存在多个版本化包 | 兼容性、activation、接口频率和命令完成语义需要实机核验 | 与现场固件完全匹配后再测试 |
| 上游 ROS 2 Admittance Controller | 控制算法软件基线 | 开源控制器，但需要符合其硬件/状态/命令接口合同 | 不会自动解决 FR5 的 SDK 延迟、网络和状态时间戳问题 | G0 通过后再集成比较 |
| KWR75 ROS 2 驱动（第三方） | 协议解析/硬件接口参考 | Humble、Ubuntu 22.04 的公开实现，Apache-2.0 | 量程常数不匹配 KWR75D；无样本级设备时间戳；多帧处理需验证 | 先 fork/审查/补测试，禁止无验证闭环使用 |

## 5. 当前证据状态

### 官方/代码材料已支持
- FAIRINO 官方 ROS 2 仓库按版本提供硬件包；SDK 头文件存在 ServoCart、状态查询与普通运动控制接口。
- 厂商 KWR75 系列页面列出了 KWR75D 的量程、采样频率、分辨率和准度。
- 公开 KWR75 ROS 2 驱动的源码包含固定的 200 N / 8 N·m 异常阈值、9.81 单位换算、主机接收时间 watchdog 和单个缓存样本接口。
- 官方仓库中存在关于特定固件/驱动组合崩溃与运动完成语义的公开用户 issue；这些是风险信号，不是普遍性结论。

### 代码可读但未实机验证
- KWR75 驱动在一次回调含多个完整帧时可能跳过较早帧。
- FR5 的 ServoCart 在目标固件上的实际调用周期、闭环带宽、反馈延迟和停止行为。
- ROS 2 service 返回码与实际运动完成状态之间的对应关系。
- 当前数采模块的输出协议、设备时间戳、实际串口吞吐和滤波延迟。

### 本项目必须实测
- FR5 型号、控制器/机器人软件版本、WebApp 版本与匹配 SDK/驱动 tag。
- KWR75D 与数采模块的准确型号、协议、单位、六轴响应、时间戳/接收时延、帧完整性和量程适配。
- 命令→实际运动频响、目标力→实测力响应以及普通停止/安全急停行为。
- 在目标力范围下，KWR75D 的有效分辨率/准确度是否足以支撑力控误差预算。

## 6. 下一步任务（交给主总控）

1. 在项目事实来源中把 G0 状态标为 **阻塞：现场版本与传感器组合未锁定**，不要把文献中的 1 kHz 或 ServoCart 频率当作本机闭环频率。
2. 现场首先记录：FR5 机械版本、控制器软件/固件版本、WebApp 版本、SDK/ROS 2 tag；KWR75D 铭牌与数采模块型号、输出接口、baud rate 和协议版本。
3. 先完成空载命令/反馈/停止测试和 KWR75D 原始数据链测试，再决定主路径是原生 SDK 自建环，还是兼容的 `ros2_control` + 导纳控制器。
4. 对 KWR75D 驱动增加逐帧解析、样本序号、接收时间与数据年龄、量程按具体型号配置、原始数据日志和已知载荷单元测试；未经这些检查不接入接触闭环。

**最终工程决策：** 当前最优策略不是立即选某个“先进力控算法”，而是把接口和传感器测量链变成可测、可审计的对象。G0 的证据将决定后续能否把固定/自适应导纳作为可部署 baseline，还是需要调整软件/通信架构或增加机械柔顺。
