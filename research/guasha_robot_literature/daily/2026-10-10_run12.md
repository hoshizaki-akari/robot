# 刮痧机器人算法链路深挖 Run 12 — 2026-10-10
## 主题：先核实 FR5 + F/T 数据链能否闭环，再挑选力控 baseline 与创新

> 本轮状态：已核验公开资料与官方仓库；没有连接实机，因此机器人固件版本、真实通信时延、反馈频率和力传感器健康状态均待台架实测。本轮不声称完成实机验证。

## 1. 本轮最多三个决策问题

### A. FR5 实际软件/指令链路是什么，能否支持所需外环？
Run 11 指出 motion-loop delay 可能是性能瓶颈。本轮先核对 FAIRINO Python SDK、frcobot_ros2 与 ros2_control 的接口要求，避免把一个仅包装 service 的接口直接当作实时闭环。

### B. 腕部六维力/力矩数据能否可信使用？
公开 SDK issue 有用户报告读数全零，以及特定固件版本下疑似通道重复的问题。这些是用户报告，不是已确认的厂商缺陷；但它们足以说明不能只检查 API 返回码，必须逐轴、已知方向并用独立参考测量验证。

### C. 当前该押注哪类控制器，还是先冻结 baseline？
当前证据支持将固定参数导纳/自适应导纳作为基线，将显式力控作为性能参照；但必须根据 FR5 实际可用接口选择。在 G0/G1 未通过之前，不把“动态接触框架 + 自适应控制”宣布为最终创新。

## 2. 本轮核验的核心资料

### 2.1 官方或上游软件资料

1. **FAIRINO Python SDK（供应商官方仓库）**  
   https://github.com/FAIR-INNOVATION/fairino-python-sdk  
   仓库说明这是 FAIRINO 协作机器人 Python SDK。发布标签采用 SDK 和机器人软件版本配对的命名方式，例如可见 Python_SDK_v2.2.6_robot_v3.9.6；近期搜索结果还出现 Python_SDK_v2.3.0_robot_v4.0.0。当前可见 release 页面快照与近期搜索结果的“最新版本”展示不完全一致，因此本轮不武断地宣布一个 universal latest：**先读取本机 FR5 控制器固件版本，再固定匹配的 SDK tag 和实际安装版本**。  
   类型：供应商官方代码/版本资料。价值：G0 版本锁定。边界：公开页面不能代替用户现场的控制器版本信息或实时性能测量。仓库标注 Apache-2.0。

2. **FAIR-INNOVATION/frcobot_ros2（供应商 ROS 2 API 仓库）**  
   https://github.com/FAIR-INNOVATION/frcobot_ros2  
   README 描述其为基于 FAIR SDK 的 ROS 2 API，将部分函数包装为 ROS service，并写明机器人软件版本需高于 V3.7.1。仓库存在名为 fairino_hardware 的目录，但本轮读取的该包 package.xml 只列出 rclcpp 和 ament_index_cpp，没有显式列出 hardware_interface、controller_interface 等标准 ros2_control 插件依赖。由此不能仅凭仓库名或目录名假定它就是可直接供上游导纳控制器加载的实时 HardwareInterface；还需要检查具体分支、源码和导出插件。  
   类型：供应商 ROS 2 API 参考实现。价值：服务调用、运动指令集成和快速联通。边界：没有证据证明 service 调用链满足刮痧力控所需的更新频率、确定性或端到端时延要求。

3. **ROS 2 上游 ros2_controllers/admittance_controller**  
   https://github.com/ros-controls/ros2_controllers/tree/master/admittance_controller  
   文档说明控制器使用 TCP F/T 传感器测得的 wrench 计算导纳；需要外部运动学插件；支持 position、velocity、acceleration 等命令/状态接口；wrench reference 必须表达在 F/T sensor frame；依赖 ros2_control 的关节状态/命令接口和 F/T sensor semantic component。参数还显式包含控制框架、传感器框架、重力补偿、末端 CoG 和滤波。  
   类型：上游通用 ROS 2 控制器及官方文档。价值：导纳控制的软件结构、参数接口和状态发布基线。边界：它不是 FR5 驱动；必须先证明 FR5 硬件层真实输出匹配的状态接口并接收所需命令接口，否则需要桥接或重新实现适配。它也不解决宽刮板 CoP 的可观测性问题。

4. **KWR75 系列 ROS 2 驱动：ian-chuang/kwr75_force_sensor_ros2**  
   https://github.com/ian-chuang/kwr75_force_sensor_ros2  
   README 声明该项目读取 KWR75 六维力/力矩传感器，并整合到 ros2_control；测试环境写为 Ubuntu 22.04 + ROS 2 Humble。其说明称通过串口协议发起连续数据流，设备端以 1 kHz 发送数据。  
   类型：第三方公开驱动，不是传感器厂家官方发布。价值：若实际硬件协议和型号匹配，可作驱动/数据链参考。边界：项目写的是 KWR75 系列，不能自动证明当前具体 KWR75D 变体、转换器、固件与线缆完全兼容；“传感器发送 1 kHz”不等于 ROS topic 时间戳质量、应用读取率或 FR5 闭环带宽为 1 kHz。仍需核验协议手册、型号和单位缩放。

### 2.3 作为控制基线的同行评审工作（复用既有证据，不算新发现）

8. **Iturrate, Iñigo; Diget, Emil Lykke; Sloth, Christoffer. “Surface Following using Direct Adaptive Admittance Control.”**  
   2025 IEEE/SICE International Symposium on System Integration (SII), pp. 1454–1459. DOI：[10.1109/SII59315.2025.10870963](https://doi.org/10.1109/SII59315.2025.10870963)。  
   IEEE 摘要说明，作者用在线法向估计调整导纳方向，并比较积分自适应律与两种 Riemannian manifold 方法；论文报告基于 Riemannian gradient descent 的方案，相比积分自适应律，将其试验中的位置误差减少 73%、角度误差减少 43%。这些数字仅适用于论文自己的平台和设置。  
   迁移：在相同硬件和轨迹上比较固定参数导纳、直接自适应导纳和局部法向先验融合；先测 FR5 真实执行器响应再解读算法性能。

9. **Piedra, Adrian; Jeffrey, R. Brooke; Khatib, Oussama. “Explicit force-based control strategies for compliant robot-assisted ultrasound imaging.”**  
   The International Journal of Robotics Research，2026-05-01 online first。DOI：[10.1177/02783649261441635](https://doi.org/10.1177/02783649261441635)。  
   作者在医疗超声平台比较显式力/力矩控制与积分自适应导纳，报告该平台力跟踪相位滞后由 121° 降至 5.76°，并报告探头朝向/远离运动时平均力跟踪误差分别降低 77.7% / 72.6%。  
   迁移：作为“若接口更底层，显式力控制可能更有响应性”的上界参照；不能将这些数字移植给 FR5。若 FR5 只有位置/速度类笛卡尔命令，就不能声称复现了该算法。

## 3. 结构化精读：接口能力决定 baseline 是否可实现

本轮重点是把三种常被混为一谈的软件路线分开。

### 路线 1：供应商 SDK 的外部笛卡尔命令回路
程序读取当前位姿和外部 F/T 数据，做 bias/重力补偿、接触状态估计，再生成下一条笛卡尔位置/速度修正。这适合先建立最小系统，但有效闭环带宽会受数据读取、网络/RPC、控制器命令执行、队列语义和实际状态反馈共同限制。它可能适合低速、低带宽的第一版基线；是否够用必须实测。

### 路线 2：供应商 ROS 2 service 包装
将 SDK 方法包装成 ROS service 有助于集成，但 service 不承诺确定执行周期或实时保证。同步调用可能阻塞；异步调用则必须处理未完成命令、过期命令、队列积压和停止时的竞争条件。需要通过源码和测量确认调用语义。

### 路线 3：标准 ros2_control 硬件接口 + 上游导纳控制器
这是一种结构清晰的实现路线，但前提是硬件层真实实现所需关节状态、命令接口、运动学与 F/T 状态接口，并且定义正确的坐标和参考点。上游控制器的 WrenchStamped 输入要求在 F/T 传感器框架中表达；若估计模块发布的是 base/contact frame wrench，必须显式转换。

**决策结论：** 实机接口没有审计前，不能宣布路线 2/3 一定优于路线 1，也不能直接照搬论文的显式力控。先制作实际接口能力矩阵，再选控制 baseline。

## 4. 最小可复现实验：G0 数据链健康检查 + G4 动态响应

### 4.1 数据链健康检查（先于任何接触控制）
1. 记录机器人固件、SDK tag、ROS 2 包分支/commit、机器人和传感器完整型号、连接方式与配置。
2. 记录原始 F/T、API 返回码、UI 读数（如可用）、机器人 TCP/joint state 和系统单调时钟。设备采样时间和消息到达时间必须分开。
3. 用已知方向静态载荷和已知力臂逐轴加载；检查响应符号、线性、重复性、零偏、温漂、轴间串扰与所有通道是否独立变化。用独立砝码/参考测力计验证；SDK 与 UI 如果共用同一内部数据源，不能算两个独立真值。
4. 检查读数卡零、丢帧/重复帧、单位或缩放错误。通道异常或版本不匹配时暂停控制试验。

验收阈值应根据厂家具体数据手册、目标力范围与工具力臂推导，不能脱离具体规格随意指定。

### 4.2 命令—实际运动频响（先无接触，再用软体体模）
1. 在确认 SDK 命令阻塞/队列语义和可靠停止方法后，做无接触、小幅度、安全的笛卡尔轨迹正弦/阶跃测试。候选频率可从 0.05、0.1、0.2、0.5、1、2 Hz 开始，但每一级是否执行取决于实际速度、幅度、硬件限制与风险分析。
2. 统一记录 t_cmd、x_cmd、t_state、x_actual、t_wrench、wrench_raw、wrench_compensated；接触测试中再记录 F_d、F_n 与 FSM_state。所有时间戳要转换到同一时钟或测得时钟偏差。
3. 指标：命令到位姿反馈延迟/抖动、有效更新率、丢弃/过期命令比例、跟踪增益、幅相响应、静态/动态力误差、峰值/超调、脱接触比例、异常停止延迟。
4. 只有数据链健康、停止机制验证、体模与试验限值批准后，才进入软体接触小扰动测试。

### 4.3 对照组与路线分支
- B0：固定参数导纳/有界笛卡尔外环（简单基线）。
- B1：Iturrate 等在线法向/自适应导纳思路（需按原论文定义复现，不从摘要猜公式）。
- B2：显式力/力矩控制作为概念性能上界；若 FR5 接口不支持所需命令/状态语义，则只能作为文献参照，不能列为已复现的对照组。
- 消融：固定视觉法向 vs 在线估计法向；固定接触点 vs 动态 CoP/contact frame；有/无 jerk/rate limiter。一次只移除一个机制。

路线决策：
- F/T、时间同步或可靠停止未通过 G0：暂停控制调参，修复数据链。
- 命令到运动延迟/抖动大：优先低频、有界修正与慢速表面跟随，或评估经验证的原生接触模式/被动柔顺；不能靠调大导纳增益解决。
- CoP 误差大：增加独立触觉/接触信息，或收窄估计声明，不要默认复杂滤波可以解决欠定问题。
- 数据链和运动环通过：再进行自适应法向/接触框架控制比较。

## 6. 本轮结论的证据分层

### 有官方/同行评审材料支持
- FAIRINO 维护 Python SDK 和 ROS 2 API 仓库；release 标签存在与控制器软件版本配对的命名方式。
- 供应商 ROS 2 API 仓库 README 描述了 service 包装；不能因此认为它具备实时性。
- 上游 ROS 2 导纳控制器对 F/T 坐标、控制框架、重力补偿、运动学与状态/命令接口有明确要求。
- 存在公开的 KWR75 系列 ROS 2 驱动参考，但当前设备变体兼容性仍待核验。
- 自适应导纳与显式力控已有真实机器人研究，平台条件与刮痧任务不同。

### 只能当作风险信号/迁移假设
- issue #20/#23/#25 的用户报告提示必须验证 F/T 数据质量，不能据此认定厂商产品缺陷。
- FR5 是否能经某一路线实现稳定、低延迟外环，不能从 API 名称推导。
- 动态 contact frame 是否减少偏载与力峰值，需要独立 CoP 真值与重复实验。

### 当前不可声称
- FR5 已支持某个频率的高带宽力控。
- KWR75D 在项目设备上的输出已达到 1 kHz、单位正确或能直接当真值。
- 供应商 ROS 2 service API 可直接与上游 admittance controller 实时组合。
- 显式力控必然优于导纳，或论文中的改善能在刮痧机器人上复现。
- 本轮已经完成本项目实机实验。

## 7. 本轮路线更新与下一轮优先级

主链不变，但 G0 更明确：在手眼和工具标定之前，必须锁定 FR5 固件/SDK/驱动版本，证明 F/T 六轴可用、时间戳可对齐、命令停止可靠，然后才允许开展力控参数实验。

下一轮优先事项：

2. 把 KWR75D 数据链做成 ROS 2 测试节点/日志工具，检查原始帧、单位、时间戳、丢帧/重复帧和通道独立性。
3. 为已知力臂夹具写 wrench 参考点变换与 CoP estimator 单元测试，明确坐标约定与符号。
