# AUBO i5 独立省力拖拽模型 V2

范围：只替换 AUBO 工作站的省力拖拽动态模型与拖拽目标生成。
设备连接、KWR75D 标定、网页操作、导出、位置牵引和恒力牵引继续复用。
本轮完成软件实现和离线验证；尚未证明实机摇头已消失。

## 为什么重构

`session_1792573840796` 的实测持续 37.88 s，正常以 `DRAG_COMPLETED` 结束。
末端相对初始姿态的最大角度为 0.521°，SDK 关节 profile 更新 9 次，运动应答
557 次，最大一次发送间隔 0.365 s。操作者仍报告严重摇头。
因此，“频繁改 profile”不是可以单独解释所有摇头的根因；这一轮也不能仅凭
“摇头”二字把问题归为大幅姿态旋转。需要核查平移、测力和位置跟随的耦合。

上一轮从相关性估计得到的约 0.3 s 不能当作已测准的固定控制器延迟。
操作者在改变方向，测力和位姿来自异步采样，没有独立的人工施力时间标记。
相关性只提示跟随滞后，不能独立证明某个 SDK 调用是唯一原因。

源码复核找到三个可明确消除的机制：

1. 旧拖拽把上一个位置目标误差带入新目标，再随最新力方向旋转前向提前量。
   这会让方向噪声作用在保留的位置提前量上，形成横向目标变化。
2. 调度时生成的绝对位置，在发送线程等待查询、求逆解或安装 profile 后，
   仍可能原样发送。移动中的末端可能已经越过该位置。
3. 松手预测分别处理六个关节；各关节得到不同的预测时间或裁剪比例后，
   不能保证整体仍是平移。按回调到达间隔直接求速度，还会被突发到达放大。

这些是结构性问题；继续叠加增益、角度阈值和方向重置补丁不利于复核。

## 新实现

### 一个三维响应模型

`fr_traction/aubo_drag_model.hpp` 不包含 ROS 或 SDK 调用。它只维护一份基座
坐标系三维速度状态：

```text
tau * dv/dt + v = mobility * radial_deadband(F_external)
tau = 0.080 s
mobility = 0.010 m/s/N
```

使用闭式离散解，避免定时器频率改变时响应系数跟着改变。三轴使用相同的
径向死区和系数，不锁定某一个主轴。换向时移除与当前力相反的旧速度分量；
松手原始测力低于释放门槛时立即清空软件速度状态。物理减速由执行端完成。
不存在位置积分、自动跟随带载零点或目标力闭环。

原有 0.65 N 启动、0.35 N 释放及 30 ms 启动确认继续使用。稳态指令灵敏度
保持线性：5 N 对应约 46.5 mm/s，10 N 对应约 96.5 mm/s；这是软件指令，
不承诺机械臂实测速度等于它。原有最高速度等约束不作扩大。

力的坐标转换使用与该次测力时间戳配对的同一份姿态完成往返。动态状态
始终保留在基座坐标系，避免把旧姿态下的状态混入当前工具坐标。

### 拖拽专用目标生成和发送

`aubo_v4_driver/aubo_drag_reference.hpp` 与 `independent_drag_reference`
分支负责拖拽目标。位置／恒力的旧调度策略不进入这一分支。

```text
target = latest_measured_position + drag_velocity * 0.060 s
```

使用既有 20 mm 单目标提前量包络；没有上一位置目标误差的递推，没有补发
迟到时间所欠的位移。固定 SDK profile 继续使用，不逐点改六关节 profile。

发送线程持有最新意图快照，按会话 epoch 区分。真正求逆解前重新读取最新
位姿、关节和意图；如果逆解期间位姿或意图改变，最多重新求解一次。profile
安装之后再次核对意图，也丢弃已经被实际末端沿施力方向越过的目标。
已经过时且未发送的目标被丢弃，下一次使用新输入；
丢弃不伪装成 SDK 运动成功，也不作为设备故障停止会话。

新增诊断字段：`drag_reference_model`、`drag_reference_reanchors`、
`drag_intent_refreshes`、`drag_intent_age_s`、`drag_superseded_commands`。

### 松手终点

松手只生成一个笛卡尔减速终点，沿短时间窗测得的平移速度方向延伸，保持
释放瞬间实测姿态，再求 IK。速度估计窗口约 80 ms，至少覆盖 30 ms；
回调突发到达不会用微秒级间隔生成速度外推。反馈不够新鲜时不进行外推。
原有独立停止通道、SDK 故障与关节连续性检查继续负责执行故障处理。

## SDK 边界

本次重写的是拖拽闭环和目标管理，底层仍使用本机已成功调用的官方旧版
`FollowModeJointMove`。这并不等于得到 FR5 的控制器内置外置传感器拖拽。
不能仅靠软件模型重构承诺消除控制柜内部跟随带宽和 RPC 抖动。

官方旧版驱动另有 TCP2CAN 周期透传和控制柜缓冲管理；如 V2 实机仍受传输
带宽限制，下一步应单独验收该传输路径，而不是把它当成已经验证可用。
本轮不在断开的控制柜上尝试切换模式。

依据：[官方旧版驱动源码](https://github.com/AuboRobot/aubo_robot/blob/master/aubo_driver/src/aubo_driver.cpp)、
[官方旧版 SDK 接口](https://github.com/AuboRobot/aubo_robot/blob/master/aubo_driver/include/aubo_driver/serviceinterface.h)
及本机安装的 V4 头文件。公开版本与本机版本存在差异，以本机编译结果和
已有真机成功记录为准。

## 验证与运行

模型测试覆盖 XYZ/斜向、正负方向、线性稳态响应、横向扰动、换向、松手、
定时器周期变化。执行端测试覆盖等待过程中改变位姿／方向、过时意图丢弃、
松手笛卡尔终点及三种模式隔离。完整结果见 `aubo_drag_v2/stage_report.txt`。

回放程序直接使用生产 C++ 模型，数据和输出保存于
`debug/session_20261021_aubo_drag_v2/`。旧位姿是旧控制器产生的测量，不能
将新指令回放的平滑程度当作新机械臂轨迹已经平滑的证明。

三份输入回放中，`1792571811589`、`1792573840796` 的全程指令相邻差分 RMS
分别降低约 28.7%、27.5%；`1792573148457` 则增加约 22.0%，持续施力片段的
指标也未改善。不能声称 V2 对全部记录都更平滑。三份回放未出现与当前力
点积为负的速度指令，但这不等于机械臂不会因执行滞后而短暂反向。

断连 ROS 回归最初收不到 `/diagnostics`。独立 Python 大消息发布/订阅也能
复现，非拖拽模型独有。测试进程使用与部署相同的 `cyclonedds_local.xml`
分片配置后恢复；未改动生产诊断 QoS，也未删除原有断连断言。

设备接好后在 WSL 运行：

```bash
cd ~/projects/aubo_i5_traction_ws/aubo_i5_traction_workstation
bash start_workstation.sh
```

该命令会完整重启并加载 V2；网页仍为 `http://127.0.0.1:8082/`。
驱动诊断中的 `drag_reference_model=aubo_cartesian_admittance_v2` 用于确认版本。
当前进入真机手感 CHECKPOINT：需判断斜向连续拖动、转弯和松手时的横摆是否
改善。离线回放通过不等于此项验收通过。
