Confirmed code defects / compatibility problem:
1. Production selected an unqualified 50 ms stream despite repeated ~300 ms
   SDK calls. Local elapsed time was not proof of controller buffer consumption.
   Socket tuning applied correctly but did not establish timing compatibility.
2. Node treated a boolean submit(false) as an SDK acknowledgement failure.
   That boolean conflated temporary BUSY with invalid/stale/revoked requests.
   The old export cannot identify which individual reject guard fired.
   This absence of evidence is not labelled as a proven network/robot fault.

Changes:
- Withdraw TCP2CAN from the production workstation node, including when old
  CLI/ROS experimental opt-ins are requested. Select existing native FollowMode
  BEFORE motion; never automatically switch protocols during an active session.
- Preserve candidate pure tests/code for investigation, not live qualification.
- Typed ACCEPTED/BUSY/REJECTED submission. One bounded, UNSUBMITTED pending slot
  may wait for a busy transport. It is cleared on stop/revoked epoch; existing
  ACK/freshness deadlines remain. No retry of a command accepted by SDK/transport.
- Real rejection records its exact guard: stopping, duplicate ID, revoked epoch,
  invalid flags/speed, nonfinite inputs or geometry/horizon/step validation.
- Diagnostics distinguish requested/effective backend, qualification, selection
  reason, pending backpressure and last submission detail.
- No force/speed/travel/ACK/health bounds were enlarged or real alarms hidden.
- FR5 checkout and original workstation were not modified.
