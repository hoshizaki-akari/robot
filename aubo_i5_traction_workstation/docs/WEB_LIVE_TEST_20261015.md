## 后续定位与当前状态（20:57）

仅修改独立 AUBO 项目，未修改原 FR5 项目。用户确认示教器没有运行程序。
数字输出通知不能作为存在其他运行程序或故障的证据。

驱动改为两个厂商连接：运动控制与遥测分开，使用厂商路点推送回调；
诊断查询在独立线程运行。读取超时仅在连续三次前有限重试；该重试不会
复位任何运动故障。发生运动故障后仍继续发布真实位姿，避免网页冻结。
增加缓冲状态、请求计数和厂商事件计数。IO 通知与其他事件分别记录。

针对本进程两个控制柜连接启用 TCP_NODELAY，并在 SDK 请求期间刷新
TCP_QUICKACK。抓包确认主机延迟 ACK 已改善，但没有解决连续运动应答阻塞。

捕获的一次 TCP2CAN 调用：请求发送约 76 微秒，SDK 随后等待应答约
312 ms；期间主机对控制器消息的 ACK 很快。其他零速度测试测得
单次发送约 91–136 ms，超过保留的 30 ms 时间间隔限制，自动停流。
这说明 ROS 状态查询阻塞不是唯一原因；尚不能仅凭这些数据断言是固件故障。
数组接口中的 FK 是本地运算，换成 vector 接口仍未解决。
未通过测试的 100 ms 相同位姿预填方案已经撤掉。
零速度测试失败不等价于已经验证所有非零轨迹必然失败。

## 非零路点对照（21:02–21:09）

增加显式 `--execute-bounded-pulse` 测试入口：基座 X+ 2 mm/s，
最多发送 0.5 秒（计划 1 mm），实测位移包络 2 mm，结束请求停止。
这不是牵引模式，也不使用未标定的力方向。静止重复路点过滤参照
[厂商驱动](https://github.com/AuboRobot/aubo_robot/blob/master/aubo_driver/src/aubo_driver.cpp)
的路点变化过滤逻辑。增加纯函数回归测试覆盖静止、XYZ 正负方向及非有限输入。

结果：

- 加入静止路点过滤后，4 次非零发送，最大观测位移约 0.067 mm；
  最后一次 SDK 调用 182.673 ms，触发原有 30 ms 间隔限制。
- 每包 4 个 5 ms 非零路点的有限对照中，首次发送仍耗时 101.045 ms；
  自动停流，停止请求返回成功。该未通过的批量参数改动已撤掉。
- 所以重复静止路点不是延迟的唯一原因；不能靠过滤静止点或 20 ms
  微批量宣称实时控制链路已修复。没有放宽看门狗，没有启用力控。
- 驱动构建通过；测试统计 22 项、0 错误、0 失败、4 跳过；Python 20 项通过。

只读 API/二进制核查表明，`robotServiceFollowModeJointMove` 走运动规划
服务；没有找到足够证据把它视为无需验证的笛卡尔伺服替代品。未向真机
试发该接口。也未修改控制柜固件、配置或安全 IO。

当前需要控制器侧日志或由厂商确认 V4.5.111 Alpha 对应的 SDK、TCP2CAN
调用/缓冲规范，才能进一步区分 SDK 兼容性、控制器调度或内部通信原因。
现有证据还不足以确认“必须升级固件”或“控制柜硬件损坏”。
用户检查点是提供匹配软件/控制器日志，而不是再次确认网线或拍安装照片。
